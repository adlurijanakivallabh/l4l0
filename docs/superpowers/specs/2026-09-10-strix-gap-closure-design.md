# Strix Capability-Gap Closure — Design Spec

**Status:** Draft, pending human approval (superpowers:brainstorming architectural path)
**Reviewed reference commit:** strix @ `f6d9790ecbc8f25739a94a22a42f430a959af737` (2026-09-03), full repository, 505 substantive files, 100% coverage confirmed
**L4L0 baseline:** `project-lalo` branch, current HEAD at time of writing (a full `/learn-codebase` pass of every `src/lalo` and `tests/lalo` file was completed in the same session immediately before this comparison; specific file/signature claims below were spot-verified against live source, not against that session's own notes)
**This document is the new baseline.** A future pass diffs against this document plus strix's git log since the commit above — it never starts over from scratch. If strix's HEAD moves, only re-read what changed since `f6d9790e`.

## 0. How this pass was run (for provenance, not to be re-litigated)

1. **Inventory.** Every file in the strix repository (505 files, ~120,700 lines across py/md/go/tsx/ts/mdx/sh/yml/json) was enumerated via `find`, excluding only images, lockfiles, `LICENSE`, and the pre-existing `REACHAGENT_COMPARISON.md` (a prior, differently-scoped comparison against L4L0's pre-rewrite predecessor — read once for background, its ReachAgent-side claims are stale and were not trusted; its strix-side claims were independently re-derived here, not copied).
2. **Full independent re-read.** Per explicit instruction, no shortcut was taken even though a complete prior strix-side comparison existed. The repository was partitioned into 22 batches by subsystem, each assigned to one parallel reader with an explicit file list, a brief on the relevant L4L0 mechanism(s), and the exact two-tier outcome test to apply. All 22 batches completed; aggregate file coverage was cross-checked against the full repository listing and reconciled to 100% (two path-normalization artifacts and 6 trivial files — `.github/*` templates, 3 tool `README.md` files — were closed by direct reading after the automated check flagged them).
3. **Adjudication.** Every one of the ~400 raw findings across the 22 batches was read in full by the orchestrating session and checked against complete L4L0 architectural knowledge (not just each batch's necessarily-partial brief). This caught and corrected roughly a dozen false positives where a batch's brief simply hadn't mentioned an L4L0 mechanism that already covers the finding (see §6, "Corrections", for the full list — most consequential: L4L0 already has a graduated NOTICE/URGENT/CRITICAL budget-warning cascade at exactly the same 70/85/95 and 75/80/85 fractions strix uses, which three separate batches independently flagged as missing).
4. **Live-source spot verification.** The highest-stakes and most-repeated claims were checked directly against current `src/lalo` source (not against memory of the earlier learn-codebase pass) before being written into this document. Every claim below that cites an exact L4L0 file/function has been verified this way; a small number of narrower mechanism-gap proposals are flagged `[unverified — confirm in planning]` where the comparison is plausible but a specific live-source check wasn't performed in this pass.

## 1. The central finding, re-confirmed against current L4L0

The prior (ReachAgent-era) comparison called finding-validation rigor "the single largest structural divergence" between the two projects. That comparison is stale — L4L0 no longer has an AST-enforced role split or a `judge()` pipeline. Re-derived fresh against the current architecture, the same underlying question resolves differently and more precisely:

**Strix's `create_vulnerability_report` tool (`strix/tools/reporting/tool.py`) validates only internal self-consistency.** Every one of its checks — counterevidence required, confidence tied to a rationale, severity-change conditions stated, a fix-verification narrative required when a fix is proposed — is a `str(x or "").strip()` truthiness check on agent-authored text. None of them independently verifies the agent's claim against anything real. The one non-self-authored check in the whole path, `strix/report/dedupe.py`'s `check_duplicate`, is an LLM judge asking "is this the same bug as an existing one," never "is this bug real." A confidently-written, internally-consistent, but entirely fabricated finding sails through every gate strix has.

**L4L0 already closes this, and does so more rigorously than strix's own methodology skills (`agentic_system_security.md`) recommend testing *other* agentic systems for.** `src/lalo/findings/grounding.py`'s `is_grounded(excerpt, evidence)` independently verifies the agent's claimed `evidence_excerpt` is a real, whitespace-normalized substring of something the agent actually captured — checking the claim against real data, not just checking the claim exists. `src/lalo/findings/confidence.py` computes a deterministic 6-component score from observed signals (reproducibility, corroboration count, specificity, cross-context reproduction, chained-impact success, evidence-provenance match), never from agent-declared severity. `src/lalo/findings/review.py`'s `run_adversarial_review` is a second, independent LLM call whose prompt payload explicitly *excludes* the finder's own description/counterevidence prose and instructs the reviewer to assume false by default and disprove using only the captured evidence shown — degrading to `open_proof_gap` on any failure, never silently confirming.

This is not a gap to close. It is documented here because closing every other real gap in this document must never touch or dilute this mechanism.

## 2. Classification legend

- **Covered** — the real-world outcome already exists in L4L0, however differently shaped. Named alongside the exact L4L0 mechanism.
- **Capability gap** — a genuinely new outcome. A concrete slot-in is proposed: almost always a skill-library playbook and/or an additive tool; a new optional spawn role only where explicitly noted as a distinct ongoing specialty.
- **Mechanism gap** — L4L0 has the coarse capability; strix's version proves a finer edge case, safety property, or correctness detail worth closing.
- **Explicit non-issue** — a strix feature deliberately not wanted, with the reasoning recorded so it is never rediscovered.

Every proposal in this document is additive capability or a correctness fix. None is a confirmation/permission/approval gate. None touches host isolation or operator-declared-targets. None uses a reference-project name inside L4L0's own code/docs/commits — patterns are described generically throughout, exactly as they must be written into the eventual implementation.

## 3. Capability gaps — concrete, prioritized

### 3.1 Passive request/response history + replay (highest-confidence gap in the whole pass)

Independently surfaced by five separate batches (tools-proxy, skills-rest, admin-docs, interface-viewer-frontend, tests-mcp-proxy-misc) reading five different parts of strix — a strong convergent signal, not five copies of one guess.

**The outcome:** every request that flows through a strix sandbox — including traffic the agent never explicitly fired (browser navigation, a shelled-out `curl`) — lands in a durable, queryable, filterable history the instant it happens, with a distinct "view one entry's raw text with in-content search" affordance and a "replay this exact captured request with just these fields changed" affordance that inherits everything else (headers, cookies, auth) rather than requiring the agent to reconstruct the whole request from memory.

**Why this survives the outcome test:** `src/lalo/execution/tool.py`'s `http`/`fire_concurrent`/`diff_responses` only ever capture a response for the specific turn that explicitly called them. Nothing durably records traffic the `browser` tool generates, and nothing lets a spawned child (which never saw the parent's turn) fetch-and-patch a request it didn't itself fire. This is a strictly larger real-world outcome than "the agent remembered to log it."

**Proposal:** a new capability inside the same disposable, no-bind-mount, no-socket container L4L0 already isolates on — never a second subsystem, never a new trust boundary:
- A container-local recording layer that the sandbox's existing outbound paths (browser tool, shell-invoked HTTP clients via `run_command`, and the `http`/`fire_concurrent` tools themselves) route through as a byproduct of using the sandbox, not a step an agent must remember.
- A filtered-listing tool action: method/host/path (substring or regex)/status/time-range, cursor-paginated, sortable.
- A view action: line-paginated raw text, or a regex search returning bounded before/after context.
- A replay-with-edits action: fetch a captured entry by id, inherit everything, patch only named fields (url / query-params-merge / headers-merge / body-replace / cookies-merge), dispatch through the existing `HttpFirer` path so it gets identical scope-check and capture treatment as any other fired request. Recompute `Content-Length` and drop any inherited `Transfer-Encoding` on a modified body (a concrete correctness detail three of the five source batches independently verified matters for tamper-and-replay).
- A derived, read-only sitemap aggregation (host → path → method+status) over the same store — no new capture logic, purely a view.
- A GUI companion panel (live traffic while a scan runs) once the data exists — purely observational, reusing the existing session/event-log plumbing.

This is additive tool capability an agent chooses to use (documented in a skill playbook), never a mandatory pipeline stage.

### 3.2 Multi-agent lifecycle gaps

Three related, independently-surfaced gaps in what a parent can do to an *already-running* child (as opposed to spawning and joining):

- **Graceful targeted stop of one running child.** Confirmed no equivalent exists (`src/lalo/agent/spawn.py`'s `build_spawn_tools`' `_spawn` function has no stop path). Today, if a root judges one of several concurrently-spawned children a dead end, the only options are waiting out the whole batch or abandoning it (which keeps silently spending shared `Budget` in the background). **Proposal:** extend `AgentCoordinator` with a per-child cooperative cancellation flag checked at the same checkpoint boundary `cancel_event` already uses, plus a `stop_agent(agent_id, reason)` tool. A stopped child finishes its current step (any already-recorded findings survive) rather than being hard-killed.
- **Selective join instead of a full-batch barrier.** Confirmed: `build_parallel_spawn_tool`'s `spawn_agents` submits all children to a `ThreadPoolExecutor` and then does `[future.result() for future in futures]` — an unconditional wait on every future in the batch, with no way to submit work and keep doing something else while only some children are needed. **Proposal:** have `spawn_agents` return immediately with child handles; add a `wait_for_agents(agent_ids=[...])` tool that blocks only on the named subset, so a parent can interleave other useful work with a running concurrent cohort.
- **Agent-to-agent redirection while a child is still running.** L4L0 already has *operator*→agent live steering (`gui/app.py`'s `POST /steer`, read every turn by `AgentLoop`'s `_pending_steering()`) — this is not a gap. What's missing is one *agent* redirecting a *sibling or child* agent's in-progress work without stopping it. Lower priority than the two above; fold into the same coordinator extension only if the stop/selective-join work makes it cheap.

### 3.3 Shared, identity-normalized baseline/threat-model artifact

Surfaced independently by three batches. A generic shared note (L4L0's `note`/`query_graph`) doesn't solve two specific problems strix's version does: (1) collapsing every spelling of the same target (a URL, a `host:port`, a git remote in ssh/https form, a local checkout path) onto one identity key so independently-working agents converge on one document instead of silently forking their own; (2) append-only, attributed amendments that survive concurrent writers, versus a generic note's full-content overwrite silently losing one of two concurrent edits.

**Proposal:** an additive record type on the same checkpointed graph state — `save_baseline`/`get_baseline`/`amend_baseline` — keyed by a normalized target-identity function (reusing whatever target-canonicalization `execution/target.py` already does), requiring a structured minimum on the full write (trust boundaries, attack surface, severity-relevant context) and a separate, non-clobbering append operation for amendments. Paired with a short methodology skill describing when to seed and consult it.

### 3.4 Coverage ledger + non-blocking finish-time summary

L4L0's `finish` (a bare early return in `agent/loop.py`) has zero mechanical surfacing of coverage today; the entire discipline lives in `closure-discipline.md`'s prompt convention. Confirmed via `tests-reporting`'s direct read of `_do_finish`: strix's version is explicitly **not** a gate — `success: True` is returned unconditionally, with a coverage-gap summary merged into the *same* successful response purely as a same-turn nudge the agent can act on or ignore.

**Proposal (two parts, both additive, neither blocking):**
1. A coverage-ledger tool family (`record_coverage`/`update_coverage`/`list_coverage`) using an outcome taxonomy (tested-and-reported / tested-and-clean / actively-ruled-out-with-evidence / not-applicable-with-reason / needs-follow-up-with-evidence), rejecting a duplicate surface+risk-area pairing in favor of pointing the caller at update, keeping prior states as history.
2. Wire a coverage-gap summary (computed from the ledger above, or — cheaper, and shippable independently — directly from the *existing* `report/coverage.py`'s `build_coverage_summary`) into `finish`'s own return value as extra informational fields. `success` is never conditioned on it.

A closely related, independently-cheap fix to `report/coverage.py` itself: strix's `_SKILL_PHRASINGS` synonym table exists because exact-match-only coverage checking produces real false "not tested" reports (a skill named `path_traversal_lfi_rfi` never string-matches a ledger row that says "Path Traversal"). L4L0's `coverage.py` does the same exact-match today. **Proposal:** add a small phrase-synonym table (skill name → the natural-language phrasings a pentester actually writes) with a meta-test pinning it against skill-library drift, exactly mirroring strix's own regression-test discipline for this. This is a report-honesty correctness fix, not a new mechanism.

### 3.5 SARIF export enrichment (all additive to data L4L0 already computes)

- **Coverage-ledger integration**: emit non-failing `pass`/`notApplicable`/`open` SARIF results for cleared/not-applicable/follow-up coverage entries, and set the SARIF invocation's `executionSuccessful` flag whenever the run didn't finish cleanly — so a CI pipeline that only ever ingests `findings.sarif` sees the same honesty guarantee `coverage.py` already provides elsewhere.
- **STRIDE tagging**: a small CWE→STRIDE lookup table (mirroring the shape, not the content, of strix's) tagging each SARIF rule for downstream dashboard filtering. Zero behavioral stakes, cheap.
- **`fixes[]` synthesis**: once §3.6 below adds structured code-location fix fields, serialize them into SARIF's `fixes` array for one-click remediation in SARIF-aware tooling.

(The PoC-embedding-in-SARIF risk that motivated a similar-looking strix finding does **not** apply to L4L0: `findings/model.py`'s `Finding` has no raw-exploit-code field at all — its docstring records that `poc_script_code` was considered and explicitly rejected in favor of evidence-provenance grounding against real captured traffic — and `report/sarif.py` does not serialize `evidence`/`evidence_excerpt` text. Confirmed covered.)

### 3.6 Structured fix-verification: code-location diffs + a verification discipline

Two related, independently-surfaced items:
- **Data**: optional structured `code_locations[].fix_before/fix_after` fields on a finding (extending, not replacing, the existing free-text `remediation` field), for source-available findings where a concrete diff is more useful than prose.
- **Methodology**: a `fix-verification-discipline.md` methodology skill teaching the ordered gates a source-visible agent should walk before attaching a proposed fix (does it actually close the issue when re-traced through the patched code; does a sibling call site/alternate input still get through; is legitimate behavior preserved; what repo checks were actually run vs. reasoned about) plus an explicit "withhold the fix, name the gap" escape hatch when it doesn't hold up.

Both are shape-only additions (never a truth gate) — filing still succeeds if an agent drops the fix fields entirely.

### 3.7 Dependency / software-composition-analysis (SCA) capability

Surfaced independently by three batches, and the single largest capability_gap by volume of supporting evidence in the whole pass. Nothing in L4L0 today distinguishes "a package is present in a manifest" from "the vulnerable code path is actually reachable" — the highest-value judgment call in SCA. L4L0's `integrations/epss.py` is enrichment (a CVE's exploitation-likelihood score) for an already-known CVE; it does not discover which CVEs apply to a target's dependencies in the first place.

**Proposal:** a new methodology skill (`vulnerabilities/dependency-cve-analysis.md` or similar) teaching: locate manifests/lockfiles (in a cloned repo or an extracted container image), resolve installed versions, run a best-in-class SCA scanner via the free shell (already installable at runtime — no new tool needed for execution), then perform a reachability check (is the flagged symbol actually imported/called) before claiming a severity. Extend the finding schema with optional structured fields (`package_name`, `installed_version`, `ecosystem`, `manifest_path`, a closed reachability enum requiring evidence unless `unknown`, and a `contextual_cvss` kept distinct from the vendor's `advisory_cvss`) so `validate_finding_fields` can enforce the same non-blank-reachability-evidence discipline it already enforces elsewhere. Given this is a genuinely distinct, ongoing specialty (parsing/version-matching/reachability-tracing is a different skill from live dynamic exploitation), it is also a reasonable candidate for an **optional** spawn role a root can choose to use alongside its existing default — never a replacement for any of them, never mandatory.

### 3.8 Skill-library breadth: net-new playbooks with no L4L0 topical home

Of the 74 non-vulnerability strix skill files read in full, the following categories have no plausible existing L4L0 file to extend — each requires a genuinely new playbook, none requires a new tool (the free shell and `http`/`browser` already reach every technique described):

- **Argument injection** (`skills-vuln`) — shell-free CLI operand/option-parser confusion, distinct from command injection (no shell breakout occurs). One new file, cross-referenced from `command-injection.md`.
- **Cloud provider-specific depth**: AWS, Azure, GCP (`skills-rest/cloud/*`) — L4L0's existing `cloud-iam-privilege-escalation.md`/`cloud-iam-storage-misconfiguration.md` are deliberately provider-agnostic; provider-exact CLI invocations and escalation-permission chains (e.g. `iam:PassRole`+`lambda:CreateFunction`, Azure's Entra-vs-ARM dual plane, GCP's `actAs`+`compute.instances.create`) need their own files. Three new files.
- **Framework-specific**: Django, FastAPI, NestJS, Next.js — genuinely framework-API-specific (DRF/Pydantic/decorator-pipeline/App-Router mechanics), not generic-vuln-class-in-disguise. Four new files.
- **Protocol-specific**: GraphQL (introspection, alias-based paired-request IDOR, federation `_entities` gaps), OAuth2/OIDC (redirect_uri bypass matrix, PKCE downgrade, code mix-up). Two new files.
- **Technology-specific**: Auth0, Electron (renderer/preload/IPC trust-boundary graph — a hybrid web-in-native-shell model L4L0's web/API-or-binary framing doesn't cover), Firebase, Grafana/Prometheus (a real, named-CVE pivot chain), an LLM-application-security umbrella (the broader OWASP LLM Top-10 surface beyond prompt injection alone — data/model supply chain, vector-store tenant isolation, excessive agency), Supabase. Six new files.
- **Reconnaissance methodology**: passive asset discovery (certificate-transparency + TLS-SAN pivoting + passive DNS + ASN/IP-range enumeration, looped to convergence) and infrastructure-lifecycle trust analysis (a broader-than-subdomain-takeover model of any long-lived external trust dependency — abandoned update channels, mail/identity domains, telemetry endpoints — with a graduated claimability ladder). Two new files; `recon/` the Python module already does spec/JS/nmap ingestion, but nothing documents the discovery *strategy*.
- **Diff-scoped review methodology** — appeared independently in three batches. This is genuinely distinct from `report/history.py`'s `diff_findings` (which diffs *output* finding-sets between two runs): it is input-scoping guidance for reviewing a single commit/PR/branch diff — what a diff newly puts in scope (a pre-existing sink it newly reaches, a shared guard it weakens even with no new code at the sink) versus what stays out of scope (an unrelated pre-existing bug merely noticed in passing). One new methodology file; the raw plumbing (`git diff`/`git show` via `run_command`) already exists.
- **Fix-verification / regression re-scan methodology** — re-testing a target's already-reported findings after remediation rather than starting recon over, when a mission names a prior scan for the same target. Folds naturally alongside §3.6.

### 3.9 Smaller, standalone additions

- **npx/package-runner supply-chain identity confusion** — a distinct technique from typosquatting or CVE scanning (proving a target-controlled workflow resolves an unintended package via a runner's own fallback/auto-fetch order). One new skill file.
- **Seed a fresh container's workspace with pre-existing content at creation, without a host mount.** Confirmed: strix achieves "get local operator content into a fresh sandbox" via bind-mounts on backends that support them and via a one-shot manifest/archive upload on backends that don't (proving the outcome never actually requires a live mount). L4L0's `RuntimeContainer` has neither path. **Proposal:** a one-shot "seed workspace at creation" capability implemented via the Docker API's own archive-upload primitive (`docker cp`-equivalent, streamed into the already-running container over the existing Docker connection) — adds zero new host-filesystem surface, since it never opens a live passthrough. Surfaced via a GUI upload affordance on the engagement-setup screen, and usable by the orchestrator to hand a freshly-spawned child bytes a sibling already produced.
- **Fetch a remote spec/collection by reference without the fetch-credential ever entering agent context.** L4L0's only mechanism for pulling anything external into a run is the agent's own shell — meaning any fetch necessarily exposes whatever credential it needs. **Proposal:** a narrow, orchestrator-side (not agent-tool) fetch step: given a mission input naming a remote reference plus an operator-supplied fetch credential, retrieve the document before the agent starts and drop only the resulting file into the workspace — the credential lives in orchestrator config/env only, mirroring the discipline `shared_redactor` already applies to keep registered secrets out of agent-visible text.
- **Spec-driven target intake improvements** — extracting an OpenAPI/Swagger/Postman spec's declared operations into recon context (not auto-authorizing its declared servers as scope — that's explicitly rejected below, §5), staging the raw spec file into the workspace so the agent can consult details an extractor missed, resolving OpenAPI server-variable templates, and (optionally) resolving a live Postman "environment" by API when a collection is written entirely in `{{variable}}` form.
- **Per-tool-output spill-to-file on truncation.** `agent/loop.py`'s `_truncate_observation` already head+tail-truncates every observation (`max_observation_chars=4000`, `_MAX_EMITTED_OBSERVATION_CHARS=2000`) — confirmed covered for the "don't blow the context budget" outcome. What's missing: once truncated, the omitted middle is gone forever short of re-running the command (not always safe/idempotent against a live target). **Proposal:** when `_truncate_observation` truncates, also write the full text to a file inside the same disposable container's workspace and append the path to the truncation notice — reuses the existing free shell, doesn't touch the redaction-at-display policy, adds no new tool.
- **Non-blocking "this model isn't in the recommended/frontier set" advisory** in the GUI's provider-configuration screen — purely informational, never blocking, reusing whatever curated-provider quality signal L4L0 already maintains.
- **Optional "sign in with an existing LLM subscription" (OAuth/PKCE) credential mode** alongside API-key entry — flagged explicitly as low-priority and requiring a deliberate human go/no-go (the underlying pattern reuses a personal consumer subscription in a way the provider may not officially support outside its own products — a ToS question, not a technical one). Not recommended for the initial implementation pass; recorded for completeness only.

## 4. Mechanism gaps — real, verify-and-fix

These are cases where L4L0 already has the coarse capability and strix's version (usually proven by a specific unit test, not just source prose) demonstrates a finer edge case worth closing.

| # | Mechanism | L4L0's existing coarse capability | The finer edge case | Proposed fix |
|---|---|---|---|---|
| M1 | Compaction trigger precision | `AgentLoop._maybe_compact_history` (fixed 12-entry window + batch of 8) | Threshold should scale with the *model's real context window* and the *actual token weight* of history content, not a fixed item count — a small-context model can overflow well before 12 entries; a huge-context model compacts needlessly early | Compute a real token estimate (system instructions + tool schema text + serialized visible history) against a per-model budget (context window minus a reserved buffer), falling back to a fixed conservative budget for unmapped models |
| M2 | Reactive overflow recovery | `AgentLoop._retry_through_provider_outage` (skips non-retryable failures) | A context-overflow rejection is usually non-retryable by the general rule, but is exactly the case worth force-compacting-and-retrying once, distinct from a genuine outage; must not misfire on a mere rate-limit throttle | Add a failure classifier that recognizes a genuine overflow shape (excluding rate-limit-shaped messages first) and forces one compaction pass before retrying that specific call |
| M3 | Statusless/network-error retry coverage | Provider adapters' own retry+backoff over a retryable-status set | A connection-level failure with no HTTP status at all (a reset, a custom OpenAI-compatible gateway's own statusless error) may fall through a closed status-code allowlist | Add a default-retry branch for exceptions carrying no status at all, excluding only explicit cancellation and already-classified non-retryable auth failures |
| M4 | Idle-stream/keepalive-defeated timeout | Per-call timeout + retry with `cancel_event` checks | A reverse proxy/gateway emitting periodic zero-byte keepalive chunks in front of a stalled LLM backend resets a naive byte-level read timeout the same way SSE keepalives do for a streaming client — even though L4L0 doesn't stream | Wrap each completion attempt in a hard wall-clock deadline independent of, and tighter than, the HTTP client's own read timeout, so intermediary keepalive traffic can't silently extend a stalled call |
| M5 | Provider content-refusal handling | `_retry_through_provider_outage`'s non-retryable-failure skip | A model provider's safety-policy refusal is a realistic, *frequent* event for this project's subject matter (credential attacks, exploit generation, RCE demonstration) — worth a distinct, labeled diagnostic rather than folding into generic retry-exhausted noise | Add a lightweight classifier recognizing a content-policy-refusal shape and log/report it under a distinct label; verify it's excluded from any retry budget so a refusal never burns retries uselessly |
| M6 | Compaction summarization discipline | LLM-based summarization once the window scrolls past | No confirmed instruction to preserve every credential/secret/finding verbatim, distinctly enumerated, never paraphrased or merged — for a tool whose entire value is the credentials/findings it discovered, this is a real data-loss risk | Add an explicit verbatim-preservation instruction to the compaction/summarization prompt |
| M7 | Compaction split-boundary safety | Same mechanism | `[unverified — confirm in planning]` Whether the split point can ever separate a recorded tool call from its own observation in a way that corrupts replay. Given L4L0's transcript entries likely bundle a call and its result into one unit (not paired provider-native items the way strix's does), this specific failure mode may not be structurally possible — verify the exact transcript entry shape before treating this as a real gap | If entries are separately paired, snap any compaction cut backward past an open (unanswered) pair; if entries are already unified per-step, close this as non-issue with a one-line note |
| M8 | MCP connection resilience | `integrations/mcp_client.py`'s allowlist, per-connection no-fallback credential, cloud-metadata URL validation, 30s session timeout | A single flat timeout stops a hang but does nothing for a transient 429/5xx/network blip — today likely either permanently breaks that connection for the rest of the run, or (worst case) an unhandled background failure could propagate onto the run's own task | Give each MCP connection its own dedicated worker/task owning connect/serve/cleanup so a background failure can't cancel the whole scan; classify failures (auth/permission/rate-limit/transport/protocol) and retry only the retryable kinds with backoff; quarantine-with-cooldown before permanent death rather than killing on the first transient error |
| M9 | MCP timeout granularity | Same 30s flat timeout | Can't distinguish a genuinely hung subprocess from a legitimately slow but healthy operation | Split into a short connect/handshake timeout and a separate, longer per-call operation timeout |
| M10 | MCP tool-name sanitization | Same allowlist mechanism | A connection name from a config file, or a tool name an arbitrary MCP server chose, can contain characters some model APIs reject in a tool name outright | Sanitize the *label* the model sees to `[a-zA-Z0-9_-]`; always dispatch using the server's own unmodified name |
| M11 | CSV/report formula-injection and fence-breakout hardening | `report/writer.py`'s CSV/Markdown renderers | `[unverified — confirm in planning]` Finding titles/evidence routinely quote target-controlled text verbatim (a reflected parameter, a banner). Verify the CSV export neutralizes a leading `=+-@`/tab/CR (CWE-1236 formula injection) and that Markdown PoC/snippet embedding widens its code fence past any backtick run already inside the content, and that control characters are stripped from titles before they hit a heading/CSV cell/list row | Add `csv_safe`-equivalent and `safe_fence`-equivalent helpers if not already present; add control-character stripping on any field allowed to quote target text verbatim, applied both at record time and on resume-hydration of an older run |
| M12 | Coverage/finding-ledger concurrency | Graph writes under `ScanRunner._graph_lock` (per prior session's own fixes to this exact bug class elsewhere) | `[unverified — confirm in planning]` Given L4L0's own recent history of partial-write/lost-update bugs in sibling subsystems (`HttpFirer`, `tcp_send_recv`, `access_control_matrix`, the narrative log), verify the coverage-ledger/finding-record check-then-insert path is a single atomic critical section under concurrent `spawn_agents` writers, and that its persistence can't let an older in-memory snapshot clobber a newer writer's already-committed row | Audit specifically for this bug class given the project's own track record; add a concurrent-writer regression test if the audit finds a real gap |
| M13 | Nullish-string tool-argument normalization | `str_arg`'s explicit-JSON-null-as-absent handling | Doesn't cover the broader family of literal strings a small/degraded model might send instead of omitting an optional argument (`"none"`, `"nil"`, `"undefined"`, case/whitespace variants) — for a scalar filter field, this silently turns "no filter" into "a filter matching nothing"; must NOT be applied to a list-typed filter's literal values | Extend the existing null-handling helper to normalize a small set of case-insensitive nullish tokens to "absent" for scalar optional arguments, leaving list-typed argument values matched literally |

## 5. Explicit non-issues (recorded so they are never rediscovered)

Reasoning is included for each — not just the verdict — since several of these look superficially compelling out of context.

- **CLI/TUI, wholesale.** Roughly a third of the entire strix repository (`strix/interface/tui/`, `strix/interface/cli.py`/`cli_args.py`/`completions.py`/`update_check.py`/`main.py`'s argparse dispatch, the Go Bubble Tea sidecar, shell-completion generation, standalone-binary self-update) is CLI/TUI presentation and distribution machinery with no GUI-transferable idea beyond "these features should exist" — which L4L0 already gets natively from being a single-process, browser-rendered GUI (real images, real HTML/CSS layout, real text selection, a direct WebSocket to the same process instead of an authenticated second-binary transport). The one genuinely transferable idea from this cluster — a resumed transcript must not misattribute internally-injected coordinator/system text to the human operator — is **not** non-issue; see §4 is the wrong table for it, it's folded into §3 as a GUI-transcript correctness note worth a light touch during implementation, not a standalone item given its low severity.
- **The entire `strix cloud` / SaaS surface.** Multi-tenant workspaces, RBAC-scoped API tokens, billing/credits/wallet flows (including a Stripe-Link top-up subprocess bridge), local-source-upload-to-cloud with a `.strixignore`/sensitive-file-exclusion policy, org/audit/webhook/connector management, a device-authorization login flow. L4L0 is local-only, single-operator, single-engagement by design, and will not gain a managed backend. The one generically-useful idiom in this cluster (least-privilege network mediation for a spawned untrusted subprocess) produces no gap: the same underlying problem is already solved more broadly by mandatory host isolation around every tool the agent runs.
- **Any gate/consent/approval mechanism, regardless of the shape it comes in.** This spans: the cloud-upload two-step SHA-256-pinned approval flow; the working-directory-mount confirmation prompt; the two-factor (session-cookie + email-verification) viewer history gate; strix's interactive-mode budget-pause-until-a-human-responds; `finish_scan`'s hard block on any still-active child. Every one of these is explicitly excluded per the hard constraint against importing gate-shaped mechanisms even in weakened form — regardless of how well-engineered the gate is. Where an underlying non-gate safety property rides inside one of these (see §4's M-items and the CSRF item below), it is extracted and proposed on its own; the gate itself never is.
- **The strix viewer's whole auth model as a design pattern to emulate.** L4L0's GUI having no auth is a documented, deliberate prior decision by the operator (reversed from an earlier token-gated design specifically to make watching a live scan easier), not an oversight this pass should relitigate. **One thing inside this cluster is not a gate and does survive as a real, separate finding, already logged in a prior session's pass on this exact topic**: strix's `SameSite=Strict` session cookie incidentally makes its mutating endpoints immune to cross-origin request forgery; L4L0's zero-cookie, zero-Origin-check GUI leaves every mutating endpoint reachable by a blind cross-origin POST from any page the operator's browser has open elsewhere. This is a request-authenticity correctness question, not an authentication one, and closing it doesn't reintroduce a gate: add an `Origin`-header validation check (reject a mismatched `Origin` on state-changing requests; allow through when no `Origin` header is present at all, so non-browser API clients are unaffected) — exactly analogous in spirit to the existing `_SAFE_RUN_ID` allowlist. **This should be treated as the single highest-priority item in this document to actually close**, since it's a live drive-by risk on the GUI as it exists today, independent of everything else here.
- **AD offensive post-exploitation tradecraft** (`technologies/active_directory.md`'s Kerberoasting, AS-REP roasting, delegation abuse, AD CS ESC1–17, NTLM coercion+relay, DCSync, golden/silver tickets). CLAUDE.md names this as an explicit, permanent non-goal distinct from the read-only AD mapping L4L0 does build. Not proposed in any form, however well the strix skill covers it.
- **Auto-authorizing a spec's declared servers/hosts as in-scope.** Strix's `api_spec.py` and its own test suite (`test_build_scope_context_authorizes_base_urls`) confirm it lets an ingested OpenAPI/Postman document's own declared base URLs become authorized attack targets purely because they appeared in a document the operator handed over. L4L0 already does the stricter, correct thing (`recon/spec_ingest.py`'s facts are always fired through the real scope-checked `HttpFirer`, never self-granting scope) — extracting a spec's *facts* to help the agent (§3.9) is fine; auto-registering its *servers as scope* is exactly the kind of convenience the operator-declared-targets line forbids, and stays forbidden here.
- **Third-party product-analytics telemetry** (PostHog/Scarf event forwarding, even in an "anonymized," opt-out form). L4L0 collects none by design. Reproducing even a redacted version would be a real confidentiality regression for a tool that runs against operator-authorized, often-sensitive engagements — this is a stronger reason than "L4L0 doesn't have a CLI," and holds even hypothetically.
- **A self-reported (agent-declared) coverage ledger, as opposed to one whose *facts* are machine-observed.** Strix's `coverage.go`/`record_coverage` mechanism is fundamentally a self-asserted "I checked X" ledger. CLAUDE.md states the opposite principle explicitly: coverage is machine-observed, not asserted. §3.4's ledger proposal above is carefully scoped to preserve this — the ledger only ever *reports what was recorded*, and coverage.py's own machine-observed FINDING/VERIFIED_SAFE distinction remains the actual honesty guarantee; the ledger is an additional queryable index over agent activity, never a replacement authority.
- **Repeated-identical-tool-call detection, tool-call-id collision rewriting, and per-turn tool-call-count capping.** All three exist in strix to manage a failure mode of native provider function-calling with per-response-restarting call-id counters and potential multi-call batches. L4L0 parses tool calls from free-text JSON (`agent/tools.py`'s `parse_tool_call`), never uses a provider's native tool-calling API, and already executes at most one call per turn (batched extras are dropped with a note, per `agent/loop.py`). None of these three failure modes can arise in L4L0's architecture. (L4L0's own repeat-call skip-then-abort mechanism, by contrast, has no strix equivalent at all — this is L4L0 ahead, not behind.)
- **Graduated budget/turn-warning cascade, root-vs-subagent warning-band differentiation, and subagent bands calibrated below the subagent reserve.** Initially raised as capability/mechanism gaps by three independent batches; corrected on verification against live source. `src/lalo/orchestrator/budget.py`'s `Budget` class already implements `_ROOT_BANDS = (0.70, 0.85, 0.95)` and `_SUBAGENT_BANDS = (0.75, 0.80, 0.85)` against a `_SUBAGENT_RESERVE = 0.90` — the identical numeric shape strix uses, independently converged, already correctly staying below the reserve threshold. `AgentLoop` already renders distinct root-vs-subagent directive text at each band into every prompt. No work needed here.
- **The concurrent budget-reserve-crossing race** strix's own tests stress-test with 25 randomized seeds. Does not apply structurally: L4L0's `check_subagent()`/`check_root()` are pure reads that raise an exception in the *calling agent's own thread* when crossed — there is no shared "notify root once" step for concurrent threads to race over in the first place, unlike strix's async broadcast-notification design.
- **Local secret-file 0600 permissions**, raised independently by three test batches as a possible gap. `core/atomic_io.py`'s `atomic_write_verified` already creates every file via `os.open(..., mode=0o600)` directly (not a later `chmod`), so there is no window, however brief, where a freshly-written file is readable at looser permissions. Universally covered.
- **Operator-supplied context overriding the authorized-target list.** Raised as a mechanism gap to verify (strix has a code-level `ValueError`-at-setup guard on top of a prompt-level instruction). On inspection, L4L0's guarantee is structurally stronger, not merely checked: `Engagement.from_specs(...)` is built exactly once, at scan start, directly from `ScanConfig.target_specs`/`exclude_target_specs` (immutable dataclass fields set before any agent runs); there is no code path anywhere by which operator steering, agent-generated text, or anything else reaches that construction site after the fact. Nothing to add.
- **PoC/exploit-script embedding in SARIF.** Does not apply: `findings/model.py`'s `Finding` deliberately has no raw-exploit-code field (its own docstring records `poc_script_code` was considered and rejected), and `report/sarif.py` does not serialize `evidence`/`evidence_excerpt` content at all.
- **Sandbox-level network-egress authorization.** Exhaustively verified absent in strix: no iptables rule, no DNS-rebinding defense, no cloud-metadata deny anywhere in `strix/runtime/`. The only network-shaping code is an optional bring-your-own Docker network attachment with zero allowlist logic of strix's own, and a MITM proxy sidecar wired purely via cooperative `http_proxy`/`https_proxy` environment variables that any non-cooperating tool (a raw socket, a Go binary, nmap) bypasses silently and unmonitored. `src/lalo/execution/scope.py`'s `ScopeGuard` — deny-by-default allowlist checked at the point every tool actually fires, a resolve-once/pin-IP cache defeating DNS rebinding, an unconditional cloud-metadata hard-deny — is a confirmed, unmatched strength. Nothing to add; recorded here explicitly because this was the single question this pass most needed to answer honestly rather than assume.
- **Container capability/privilege posture and host-mount protections.** Strix's containers run looser (full default capability set plus an unconditional `NET_ADMIN`, no `no-new-privileges`, and `pentester` has unrestricted `NOPASSWD` sudo) — L4L0's `--cap-drop ALL` + minimal explicit re-adds + unconditional `no-new-privileges` is strictly more careful, and L4L0's baseline `SYS_PTRACE` grant is actually a superset of strix's own pwn/debugging capability (strix never grants it at all). Strix's extensive host-directory mount-denylist (`.ssh`, `/etc`, home root, etc.) exists only because strix supports live host bind-mounts at all; L4L0's `RuntimeConfig` has no bind-mount option whatsoever, eliminating the entire vulnerability class by construction rather than needing to sanitize it after the fact. Nothing to add in either direction.
